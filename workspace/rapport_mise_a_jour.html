Rapport Technique - Mises a jour NEMESIS CLI

Date : 27 avril 2026

Projet : /home/nemesis/Projets/nemesis_cli

Version : 1.1 - Stable

1. Resume des modifications

La version 1.0 de NEMESIS CLI etait fonctionnelle mais presentait plusieurs limitations : un service d'upload casse (antibot), une lecture de fichiers inefficace (contenu brut envoye a l'IA), des timeouts bloquants pour les taches longues, et des bugs dans le dispatcher d'actions.

Cette mise a jour corrective et evolutive apporte 5 ameliorations majeures et corrige 3 bugs critiques.

2. Modifications par fichier

2.1 uploader.py - Refonte complete du systeme d'upload

Probleme initial : 3 services (tmpfiles, pixeldrain, gofile) avec une cle API en dur, tous bloques par des antibots. Aucun fallback fonctionnel.

Solution : Test systematique de 22 fournisseurs via un script dedie. 6 fournisseurs retenus, integres en cascade avec fallback automatique.

2gofile.ioOK

Suppressions :

  • Cle API Pixeldrain en dur (9b440fb9-dcd6-4cf4-9cec-9c8eb1e4c64c) - faille de securite
  • Anciens services : _upload_tmpfiles, _upload_pixeldrain, _upload_gofile (remplaces)
  • Module shutil et methode is_cloudflared_available (code mort)

2.2 tools.py - Nouveau systeme de lecture de fichiers

Probleme initial : L'action read renvoyait le contenu brut des fichiers dans le message, saturant le contexte de l'IA. De plus, le dispatcher etait corrompu avec des blocs en double.

Solution : Methode read_file() repensee :

  • 1 fichier : conversion en .txt (nomFichier.txt), upload, lien retourne a l'IA, suppression du .txt temporaire
  • N fichiers (max 15) : fusion dans code.txt avec separateurs, un seul upload, un seul lien
  • Fichiers originaux jamais modifies
  • Nettoyage automatique des .txt temporaires via bloc finally

Format du fichier genere :

=== main.py === (contenu du fichier python) ============================================================ === config.yaml === (contenu du fichier yaml)

Corrections de bugs :

  • Suppression du double bloc elif action_type == "read" dans execute_action
  • Correction de execute_upload (structure corrompue)
  • Correction de execute_html_to_pdf (bloc except orphelin)

2.3 bridge_client.py - Suppression des timeouts

Probleme : Timeouts stricts (5s, 10s, 30s, 60s, 300s, 600s) empechant les taches longues.

Solution : Tous les parametres timeout passes a None. Boucle de polling while True (plus de limite de temps).

  • Section Lecture de fichiers reecrite : format multi-fichiers avec separateur |, max 15 fichiers, explication du systeme de conversion .txt + upload
  • Section Upload de fichiers ajoutee dans les outils specialises
  • Suppression des references a 0x0.st et cloudflared (remplaces par les 6 fournisseurs)

2.5 agent.py - Aucune modification

Fichier stable, aucune modification necessaire. La boucle interactive, le parsing des actions et le formatage du feedback restent in changes.

3. Architecture finale

NemesisCLI (agent.py) ├── BridgeClient (bridge_client.py) → API Bridge Android (timeout=None) ├── ActionExecutor (tools.py) │ ├── list_dir, read_file*, write, append, patch, bash │ ├── execute_upload, execute_html_to_pdf, execute_pdf_to_text │ ├── check_process, kill_process, cleanup_logs │ └── update_tracker └── FileUploader (uploader.py) ├── litterbox (primaire) ├── gofile.io ├── tmpfiles.org ├── uguu.se ├── x0.at └── temp.sh (dernier recours)

4. Scripts auxiliaires

test_upload.py (dans workspace/) : Script de test autonome qui a permis de debusquer les 6 fournisseurs fonctionnels parmi 22 candidats. Resultat : 6 succes, 16 echecs.

5. Points de vigilance

  • Les 6 fournisseurs d'upload sont des services tiers gratuits. Ils peuvent changer leur politique a tout moment.
  • L'absence de timeout peut bloquer indefiniment si le Bridge Android est deconnecte. L'utilisateur doit faire Ctrl+C.
  • Les fichiers .txt temporaires sont supprimes automatiquement, mais en cas de crash brutal, un nettoyage manuel peut etre necessaire.

6. Conclusion

La version 1.1 de NEMESIS CLI est operationnelle et stable. Les 3 bugs critiques ont ete resolus, le systeme d'upload est resilient avec 6 fournisseurs en cascade, la lecture de fichiers est optimisee pour ne jamais saturer le contexte de l'IA, et les timeouts ont ete supprimes pour permettre les taches longues.

Prochaine etape envisagee : Implementation du fallback cloudflared tunnel pour une autonomie totale sans services tiers.
