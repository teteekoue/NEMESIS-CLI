# FICHE TECHNIQUE — NEMESIS DESKTOP

---

## 1. ÉTAT ACTUEL : NEMESIS CLI (Fonctionnel)

### Architecture
```
nemesis-cli/
├── agent.py                 # Boucle interactive, parsing actions, communication IA
├── bridge_client.py         # Client HTTP pour API Bridge Android
├── tools.py                 # Exécuteur d'actions (bash, read, write, patch, pdf, upload)
├── uploader.py              # Upload fichiers vers 5 services en cascade
├── context_manager.py       # Gestion sessions JSON pour historique conversations
├── config.yaml              # Configuration bridge (host, port)
├── prompt_system.txt        # Instructions système pour l'IA
├── requirements.txt         # pyyaml, rich, requests
└── workspace/               # Bac à sable
```

### Fonctionnalités actuelles
| Action | Description |
|--------|-------------|
| `bash` | Exécution commandes shell (synchrone/asynchrone, timeout 5 min) |
| `read` | Lecture multi-fichiers → upload → lien public |
| `write` | Création/écrasement de fichiers avec contenu protégé |
| `append` | Ajout à un fichier existant |
| `patch` | Modification via diff unifié (fuzz=2) |
| `list_dir` | Exploration arborescence |
| `validate` | Vérification syntaxe Python/Bash |
| `upload` | Upload fichier → 5 fournisseurs en cascade |
| `html_to_pdf` | Conversion HTML → PDF (LibreOffice) |
| `pdf_to_text` | Extraction texte PDF |
| `stop_all` | Arrêt processus asynchrones |
| `status` | Vérification état processus |
| `cleanup_logs` | Nettoyage logs terminés |

### Communication IA
- **Mode Bridge** : HTTP POST → API Bridge Android → polling /result
- **Mode Proxy** : HTTP POST → DeepSeek Proxy local (localhost:8000/v1)
- **Parsing** : Extraction balises `<ACTION>` protégées dans blocs de code

## 2. CIBLE : NEMESIS DESKTOP (Tauri)

### Stack technique

| Couche | Technologie | Justification |
|--------|-------------|---------------|
| **Interface** | HTML5 + CSS3 + JavaScript | Rendu riche, animations, responsive |
| **Moteur de rendu** | WebKitGTK (intégré Linux) | Pas de navigateur, pas de Chromium |
| **Backend** | Rust (Tauri) | Binaire compilé, performance native |
| **Logique métier** | Python 3 (agent.py, tools.py) | Code existant réutilisé intégralement |
| **Communication** | Rust ↔ Python via stdin/stdout JSON | Pas de HTTP, pas de socket |
| **Packaging** | GitHub Actions | Compilation croisée 32/64 bits |

### Communication Rust ↔ Python

```
Interface (JS)
    │ invoke('send_message', {text: "salut"})
    ▼
Rust (Tauri Command)
    │ stdin → JSON {"command": "send", "message": "salut"}
    ▼
Python (agent.py --mode=ipc)
    │ Traitement via bridge_client.py
    │ stdout → JSON {"type": "response", "text": "Bonjour..."}
    ▼
Rust (Tauri Command)
    │ emit('ai_response', data)
    ▼
Interface (JS)
    │ Mise à jour du chat
```

## 4. PROTOCOLE IPC (Inter-Process Communication)

### Format des messages

```json
// Rust → Python (requête)
{
  "id": "req_001",
  "command": "send_message",
  "params": {
    "message": "salut",
    "session_id": "20260504_test",
    "auto_approve": false
  }
}

// Python → Rust (réponse)
{
  "id": "req_001",
  "type": "response",
  "data": {
    "text": "Bonjour ! Je suis NEMESIS...",
    "action": {
      "type": "list_dir",
      "content": "./workspace"
    }
  }
}

// Python → Rust (événement asynchrone)
{
  "id": null,
  "type": "event",
  "event": "log_line",
  "data": {
    "block_id": "sync-bash",
    "line": "$ ls -la\n"
  }
}
```

### Cycle de vie d'un message

```
1. JS: invoke('send_message', {message: "salut"})
2. Rust: commands.rs → serialize → stdin Python
3. Python: agent.py traite → bridge_client → IA
4. Python: stdout → JSON response
5. Rust: deserialize → emit('ai_response', data)
6. JS: listener → mise à jour UI
7. Si action: JS: invoke('approve_action', {choice: "y"})
8. Rust → Python → exécute tools.py → feedback → JS
```
